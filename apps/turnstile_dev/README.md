# Turnstile dev

What this repository's suites need and no adopter does: the ephemeral Postgres cluster, the sandbox setup, the schema-dump task, the engine launchers, and the test that holds the umbrella's source tree to its shape. Nothing here ships to Hex; every package takes it as `{:turnstile_dev, in_umbrella: true, only: :test}`, so nothing it holds can be called from a published package's `lib`, and Boundary checks that.

- `Turnstile.Dev.Cluster`: the cluster `mix test` starts. `start/1` runs `initdb` into `tmp/pg-<random>/`, starts Postgres on a unix socket with no TCP port, creates the owner and application roles and the sandboxed and committed databases, runs the migrations the caller names as the owner, configures the test repos, and registers the stop. `docs/contributing.md` §2 has the steps.
- `Turnstile.Dev.Sandbox`: what every case template's `setup` calls to check out a sandboxed connection, and the truncation a committed test runs instead.
- `Turnstile.Dev.SchemaDump` and `mix turnstile.schema_dump`: raise a cluster, run a thin application's migrations as the owner, and write `pg_dump --schema-only` into `priv/schema/<adapter>.sql`, which CI diffs. The task runs in the test environment, because that is where the connection library it needs is loaded.
- `Turnstile.Dev.Cerbos`: one `cerbos server` per `mix test` run, and one owned by a single test where that test publishes a policy version the run's sidecar must not see. It writes a configuration file naming the caller's policy directory and a free port of the loopback interface.
- `Turnstile.Dev.Fga`: one `openfga run` per `mix test` run with the in-memory datastore, and one owned by a single test where that test needs a store the run's server must not see.
- `StructureTest`, in this package's own suite: reads every `.ex` file under each package's `lib` and `test/support` from the syntax tree and holds it to the placement rules of `docs/design.md` §6. The path names a module the file defines, every other module in the file is named under it, a module under `domain/` calls nothing that touches the world and names no module under `application/` or `infrastructure/`, a module under `infrastructure/` names no module under `application/`, and in a published package the modules under the three places carry `@moduledoc false`. It starts nothing and depends on nothing it reads; `@exceptions` names each file that cannot follow the path rule, with its reason.

Both launchers start the process under `MuonTrap.Daemon`, which kills it when the Erlang process that owns it dies and when the virtual machine exits, and both wait on the server's health endpoint through `Turnstile.Dev.poll/2` before they answer, so a caller never asks a server that is not listening yet. Starting an operating-system process takes `muontrap`, and a published adapter carries no dependency its own users have no use for, which is why the launchers are here.
