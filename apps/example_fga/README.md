# The example on a relationship graph

The controlled-unclassified-information example of `turnstile_example`,
bound to the `Turnstile.Fga` adapter. This application is thin: it boots the
configuration, binds the model file, the tuple mapping, and the guard to the
example's repo, declares what each rule of the example is enforced by, starts
the projector, and carries the migrations. The domain, its contexts, its web
layer, and every scenario live in the example; the mechanism lives in the
adapter.

The rules are a model a server holds. A model declares types, the relations
of each type, and how a relation is computed: assigned directly, from another
relation on the same object, or through a related object, which is how
"members of the document's program" is written. The facts are tuples of
`(user, relation, object)` in a store, and the store is a copy of the ledger
that the projector keeps current rather than the application's own tables.
So this binding requires a ledger: there is no mode in which the facts reach
the engine without one.

## What is here

- `ExampleFga.Application`: boots `Turnstile.Config` with the server's address, the store, and the ledger from the application env, binds `Example.Repo`, the model file, the mapping, and the guard, starts the repos and the projector, and publishes the model as a policy version.
- `ExampleFga.TupleMapping`: which objects a fact event can have changed, and which tuples the fold requires of an object. Both questions are answered from the fold, which is what lets the projector write differences rather than translate events.
- `ExampleFga.Guard`: the re-authentication window, read from the environment before the server is asked, for a fact about the session that no tuple should carry.
- `ExampleFga.Capabilities`: the capability level of every rule, with the component that enforces it.
- `priv/fga/model.fga`: the model as text, which is the artifact under review and what a policy version carries as its content.
- `priv/repo/migrations/`: the example's tables and the ledger through the helpers the library packages ship, then the projector's checkpoint table, one row per store.
- `priv/schema/fga.sql`: the schema the migrations produce, regenerated by `mix turnstile.schema_dump` and compared in the gate.
- `config/config.exs`: `FGA_ENDPOINT`, `FGA_STORE_ID`, the drain interval, and the ledger this application boots with.
- `config/test.exs`: the endpoint and the store boot validates against the adapter's schema, and the repos left to the ephemeral cluster, so the projector is the tests' to drive.

## The example's words in the model's words

| The example says | The model says |
|---|---|
| A program member or a program lead | `user:U member program:P`, `user:U lead program:P`, written while the program is open and deleted when it closes |
| A designating office's designator or approver | `user:U designator office:O`, `user:U approver office:O`, one tuple per office-role row, so an account holding both roles in one office holds both relations |
| An office of an agency | `agency:A agency office:O` |
| A document's program and designating office | `program:P program document:D`, `office:O designating_office document:D` |
| A portion of a document | `portion:X portion document:D`, `document:D document portion:X` |
| A control the banner carries | `user:* fedonly_applies document:D` and the three flags beside it, a wildcard meaning the control applies to everyone |
| A category the banner names | `category:C category document:D`, and the same on a portion that names one |
| A specified category's implied controls | `user:* fedonly_applies category:C`, reached by `fedonly_applies from category`, so nothing is copied into the document |
| A decontrol date | `before_decontrol` with the date on the flag and category tuples, compared with `current_time`, which the adapter sends with every question |
| The releasing countries | `country:CC releasable_to document:D`, cleared by `member from releasable_to` |
| A named list | `user:U listed document:D`, which combines with nothing else |
| An account's employment and nationality | `user:U member employment:federal`, `user:U member country:CC`, the value reified as an object because a graph compares by walking |
| An agency's nationality and its own staff | `country:CC domestic agency:A`, `employment:federal federal agency:A` |
| The override permission | `user:U operator agency:A`, held outside any agency and so an operator of each |
| A marking proposal | `office:O office proposal:R`, `user:U proposer proposal:R`, and the approval is the approver less the proposer |
| Who is asking | `user:U`, the user of every check, whatever kind the subject carries |
| Re-authentication within the window | nothing: the guard reads it from the environment before the server is asked |
| The version the decision was made under | the id the server gave the model when it was published |

## The mechanism per rule

| Rule | Mechanism | Enforced by |
|---|---|---|
| C1 Lawful purpose | `lawful_purpose`, the members of the document's program or of its designating office | the engine |
| C2 Controls, all of | `can_read: lawful_purpose but not blocked`, where each flag that applies must be cleared and an absent flag blocks nobody | the engine |
| C3 Specified categories | the category carries its own flags and the document inherits them through `from category`, so a category that is not specified implies nothing by having no flags | the engine |
| C4 Banner | the document's flags include `from portion`, so the banner is the union by construction as well as at write time in the domain, and the redacted read is `can_read_redacted` on the document with `can_read` per portion | the engine |
| C5 Decontrol | the condition `before_decontrol` on the tuples a date lapses, holding the date, against the moment of the question in the context, so a date that passes needs no write | the engine |
| C6 Named list | `listed`, a grant per document, with no path from it to `lawful_purpose` | the engine |
| C7 Marking gates | `can_change_marking` and the relations computed from it; the write itself is refused by the seam before the model is asked | the seam |
| C8 Re-authentication | the guard the binding names, which reads `reauthenticated_at` from the environment and refuses before the call | the adapter |
| C9 Separation of duties | `can_approve_marking: approver from office but not proposer`, on the proposal | the engine |
| C10 Audited override | `can_override` in the model, with the permission, the justification, the event, and the report in the example's code | the application |
| C11 Continuous evaluation | every check walks the tuples the store holds, up to the position the projector has drained to, which each decision reports | the engine |
| C12 Revocation clock | measured and recorded beside the configured maximum, the drain included, never asserted | the adapter |
| C13 Scope fidelity | `ListObjects` under the cap becomes a rule over identifiers, and at the cap or above it the answer is short of the truth without saying so, so the seam asks per page instead (limited) | the engine |

## The model id is the version

A model is immutable and the server names it by id, so the version identifier
every decision carries is that id and no configuration states it. What decides
whether a boot publishes anything is the digest of the text: a text whose
digest the ledger's latest version already carries needs no second model, and
a text that changed by a character needs one. A published version carries the
text as its content under the cap, which is what makes a replay a store of its
own on a throwaway server rather than a checkout.

Two things follow. A rule change reaches every question at once, because a
question moves to another model by being asked under another id rather than by
waiting for anything to propagate. And an id belongs to the store that issued
it, so the id a replay comes back with is not the id the decision named; what
the two share is the text, and the version event carries its digest.

## Running the suite

```
mix turnstile.schema_dump && git diff --exit-code priv/schema/
mix test
```

The test helper starts an ephemeral cluster, runs the migrations as the owner
role, and starts both repos on one database, so the committed scenarios can
truncate what they wrote. It then starts one `openfga run` with the in-memory
datastore on a free port, and each test creates a store of its own on it: the
store is the engine's copy of the facts, and two tests sharing one would read
each other's tuples whatever the database does with their rows. Every scenario
that writes a fact settles the projector before it asks, since a tuple reaches
the store by a drain rather than by the write. The dump task raises a cluster
of its own, and runs in the test environment because that is where the
connection library it needs is loaded.
