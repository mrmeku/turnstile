# The example under RBAC in code

The controlled-unclassified-information example of `turnstile_example`,
bound to the `Turnstile.Code` adapter. This application is thin: it boots
the configuration, binds a policy module to the example's repo, declares
what each rule of the example is enforced by, and carries the migrations.
The domain, its contexts, its web layer, and every scenario live in the
example; the mechanism lives in the adapter.

## What is here

- `ExampleRbac.Application`: boots `Turnstile.Config` with the adapter and the ledger mode from the application env, binds `ExampleRbac.Policy` to `Example.Repo`, starts the repos and the audit store, and publishes the policy version.
- `ExampleRbac.Policy`: the role table and, per protected schema, the grants and predicates. A program role reaches a document through its open program and a portion through its document; an office role reaches a document through its designating office and a proposal through the document's office.
- `ExampleRbac.Predicates`: the hop filter for an open program, the controls subquery, the session check, and the separation-of-duties check, as `dynamic` expressions the adapter puts in every rule.
- `ExampleRbac.Capabilities`: the capability level of every rule, with the component that enforces it.
- `priv/repo/migrations/`: the example's tables and the ledger's counter, through the helpers the library packages ship.
- `priv/schema/rbac.sql`: the schema the migrations produce, regenerated by `mix turnstile.schema_dump` and compared in the gate.
- `config/test.exs`: `EXAMPLE_LEDGER` selects the ledger mode of a test run.
- `config/dev.exs`: the development database `nix run .#services` raises, and a ledger, which a review of a past date is the fold of.
- `priv/seed.exs`: two accounts assigned to a program in March and one of them revoked in April, so a review can be asked about a date either side of the revocation.

## The example's words in the adapter's words

| The example says | The policy says |
|---|---|
| A program member or lead | `role :member`, `role :lead` |
| A designating office's designator | `role :designator` held through `Example.OfficeRole` |
| An approver of the office | `role :approver` held through `Example.OfficeRole` |
| A document of a program | `grant :assignment` with `on: :program_id` through the open program |
| A document of an office | `grant :office` with `on: :designating_office_id` |
| The banner's controls, the categories' implied controls, the decontrol date | `predicate :controls` on `read` |
| Re-authentication within the window | `predicate :session` on the marking operations |
| A different approver | `predicate :another_approver` on `approve_marking` |

## Running the suite

```
EXAMPLE_LEDGER=none mix test
```

The test helper starts an ephemeral cluster, runs the migrations as the
owner role, and starts both repos on one database, so the committed
scenarios can truncate what they wrote.

## Reviewing a date

The suite's cluster lives and dies with one run, and a review of a date is
asked of a database that outlives the question, so the review runs against
the development one. In another terminal:

```
nix run .#services
```

Then, from this directory:

```
mix ecto.migrate -r Example.OwnerRepo --migrations-path priv/repo/migrations
mix run priv/seed.exs
mix turnstile.review --at 2026-04-02
mix turnstile.review --at 2026-03-31
```

The first review is of a date after the revocation and reports one account;
the second is of the day before it and reports both. Neither reads the
tables: the rows of a past date are the fold of the ledger stopped at the
end of that date, which is why the development configuration names one.
